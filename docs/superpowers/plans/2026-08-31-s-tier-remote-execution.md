# S-tier Remote Execution — Reuse-first Shared exe.dev Nodes

> **For agentic workers:** Execute one task at a time with a fresh sub-agent per
> task. Preserve each commit boundary. This plan deliberately extracts and
> reuses the existing CLI executor; do not build a parallel runtime.

**Goal:** Let `ox remote` provision or select an exe.dev node and start durable
background ox conversations there, while reusing the local CLI's broker,
`AgentPool`, `ThreadRegistry`, Wasmtime execution, tool sandbox, inbox,
ledger, approval, and crash-recovery machinery.

**Scope:** Rust CLI, a reusable packaging of the existing execution core, a
thin headless worker and public Store, StructFS transport over RuSSH, exe.dev
control, durable local orchestration, and operational hardening. Flutter,
Android, Kotlin, and a new Isotope scheduler/runtime are out of scope.

**Correction to the earlier plan:** Conversation processes, a second node
catalog, supervisor-to-child proxies, a second event journal, and a new
conversation scheduler were over-design. Wasm execution and sandboxed tool
subprocesses are the isolation boundaries. Existing per-thread workers provide
concurrency, not security isolation. This plan keeps that architecture.

**Normative spec:**
[`2026-08-31-ox-remote-cli.md`](../specs/2026-08-31-ox-remote-cli.md), amended
by Task 0 so one-conversation-per-node is a rollout policy rather than a data
model limitation.

**Tech stack:** Rust 2024, Tokio, StructFS, `ox-broker`, `ox-inbox`,
`ox-runtime`, Wasmtime, `ox-tools`, SQLite/WAL, CBOR, RuSSH, exe.dev SSH API.

## Reuse budget

The remote project starts with a hard constraint: **new code may wrap, expose,
or harden the local executor, but may not reimplement it.**

| Capability | Existing owner to reuse | Permitted remote work |
|---|---|---|
| conversation creation/index | `InboxStore` | idempotent remote acceptance mapping |
| conversation namespace | `ThreadRegistry` | public path adapter only |
| concurrent conversation execution | `AgentPool` worker-per-thread model | headless control handle and limits |
| Wasm execution | `AgentRuntime` / `AgentModule` | configurable resource/cancel controls |
| filesystem/shell tools | `ToolStore` + `ox-tool-exec` | fail-closed Linux policy validation |
| approvals | `ApprovalStore` and thread approval paths | remote record adapter |
| durable log | `SharedLog` + per-thread `LedgerWriter` | ledger cursor projection |
| crash restore | snapshot restore, classifier, resume prologue | invoke unchanged on worker restart |
| broker routing | `BrokerStore` + `mount_async` | headless mount composition |
| config/secrets | existing config and separate `secret/` mount | worker configuration, no flattening |

Before adding a new table, queue, state machine, Store, or log, an implementing
agent must record why the existing owner cannot carry the requirement. “Remote
needs one too” is not sufficient.

## S-tier concurrency claim

One node runs one long-lived `ox-worker serve` process containing the same
execution core as the local CLI. It may have many conversations:

- `AgentPool` retains one lightweight worker thread and mailbox per active
  conversation;
- `AgentRuntime`/compiled `AgentModule` are shared;
- each `AgentModule::run` creates a fresh Wasmtime Store and instance for that
  turn against the conversation's existing StructFS namespace;
- each thread keeps its own `SharedLog`, `LedgerWriter`, and approval state;
- the existing pool is minimally generalized from one pool-wide workspace to a
  per-thread workspace configuration, while local CLI keeps using its current
  single workspace for every local thread;
- filesystem and shell calls remain external `ox-tool-exec` invocations under
  the sandbox policy.

A conversation blocked on approval or model I/O must not hold the execution
core's control mutex or broker server loop. Other conversation workers continue
independently. Finite CPU, memory, disk, and provider quotas can still cause
contention; the worker exposes bounded admission and explicit overload rather
than pretending resources are infinite.

No per-conversation OS process is introduced. If stronger host-level tenancy is
ever required, the placement policy assigns those tenants separate exe.dev
nodes; it does not fork the ox architecture in two.

## Design properties

1. **One executor.** Local CLI and remote worker instantiate the same extracted
   `ExecutionCore`; behavior differences are adapters and policy configuration.
2. **StructFS across component boundaries.** CLI/coordinator/worker operations
   are Store reads and writes. SSH, stdio, and Unix sockets are carriers.
3. **Existing thread ID is the worker conversation ID.** The worker returns the
   `t_...` generated by `InboxStore`; no competing conversation identity is
   invented on-node. The local coordinator may retain its own stable remote
   reference.
4. **Placement is separate from execution.** Nodes support many thread IDs.
   `fresh_node`, `prefer_existing`, and `require_node` are policies, not schema
   cardinalities.
5. **Ledger is the event stream.** Remote cursors project existing
   `LedgerEntry { seq, hash, parent, msg }`. There is no second event journal.
6. **Commit before visibility remains unchanged.** Remote exposure cannot see a
   log entry before its existing `LedgerWriter` commit.
7. **Replay remains unchanged.** `ThreadRegistry` restores without durability,
   installs the writer, classifies the tail, and drives resume exactly as local
   CLI does.
8. **Idempotency is added at ingress only.** Stable create/message/approval/
   cancel IDs prevent transport retries from invoking existing executor actions
   twice. The accepted intents live in the worker's existing `ox.db`.
9. **No broker head-of-line blocking.** Public worker and remote proxy Stores use
   `mount_async`; parked cursor reads are independent futures.
10. **SSH lifetime is irrelevant.** `ox-worker serve` owns the execution core.
    `ox-worker structfs-stdio` is a stateless bridge to its Unix Store socket.
11. **Tool isolation is fail-closed remotely.** A remote worker never selects
    `PermissivePolicy`; sandbox compilation/enforcement failure rejects the tool.
12. **Native tools are trusted host capabilities.** The remote allowlist contains
    only audited adapters. Untrusted filesystem/shell work uses `ox-tool-exec`.
13. **Overload is explicit.** Limits bound active turns, queued prompts, cursor
    reads, frame bytes, and artifact bytes. Control/approval/cancel paths do not
    queue behind turn admission.
14. **No local daemon required.** The remote worker owns background progress;
    local commands reconcile on demand.
15. **No secret replication.** SSH keys, provider credentials, and secret Store
    snapshots never enter remote creation records, ledgers, or event cursors.

## Target architecture

```text
local ox remote command
  -> RemoteManagerStore
       -> local InboxStore remote-operation rows
       -> ExeControlStore
       -> RemoteStore (StructFS over RuSSH)
            -> ox-worker structfs-stdio
                 -> Unix socket
                      -> long-lived ox-worker serve
                           -> ExecutionCore (same as local CLI)
                                ├── BrokerStore
                                │    ├── inbox/   InboxStore
                                │    ├── config/  ConfigStore
                                │    ├── secret/  ConfigStore
                                │    └── threads/ ThreadRegistry
                                ├── AgentPool
                                │    ├── worker t_a
                                │    ├── worker t_b
                                │    └── worker t_c
                                └── WorkerPublicStore (thin adapter)
```

### What `ExecutionCore` is

`ExecutionCore` is a packaging of current code, not a replacement runtime:

- the current `AgentPool` and worker loop;
- the current `ThreadRegistry` and `ThreadNamespace`;
- the common subset of current broker setup;
- the current config snapshot, commit drain, policy, tool, Wasm, approval, and
  resume paths;
- a per-thread `ThreadExecutionConfig` carrying workspace and policy profile;
  local construction supplies the same pool-wide workspace it uses today;
- a headless command channel so UI code and `WorkerPublicStore` do not need
  mutable access to `AgentPool`.

The command channel owns the pool and accepts bounded commands such as
`CreateThread`, `EnsureWorker`, `EnqueuePrompt`, and `Shutdown`. These are quick
control operations; actual turns remain on the existing per-thread workers.
Approval reads/responses continue through broker paths rather than the command
channel.

When a full Isotope runtime replaces today's pre-Isotope harness, it replaces
the internals behind `ExecutionCore`; the remote protocol and worker do not fork
or pre-implement that future runtime.

### Worker Store

The worker exposes only:

```text
read  health
read  capabilities
read  capacity

write conversations <CreateConversation> -> conversations/<thread_id>
read  conversations
read  conversations/<thread_id>
write conversations/<thread_id>/messages <RemoteMessage>
read  conversations/<thread_id>/ledger/from/<seq>
read  conversations/<thread_id>/result
read  conversations/<thread_id>/approvals/pending
write conversations/<thread_id>/approvals/<approval_id> <ApprovalResponse>
write conversations/<thread_id>/control/cancel <CancelRequest>
```

The adapter translates these paths into existing operations:

| Public operation | Existing machinery |
|---|---|
| create | `InboxStore` thread create + `AgentPool::ensure_worker` |
| initial/follow-up message | durable ingress row, then existing prompt mailbox |
| summary/result | inbox thread row + existing log/history projection |
| ledger cursor | bounded projection of existing `ledger.jsonl` envelopes |
| pending approval/response | existing `threads/<id>/approval/*` paths |
| cancel | new cancellation control added to existing worker/runtime seam |

It never exposes arbitrary broker paths, filesystem paths, tools, config,
secrets, or commands.

### Minimal worker persistence

The worker uses its normal inbox root and normal `ox.db`. `ox-inbox` adds only
the ingress metadata that current local calls do not need:

```sql
worker_creates(create_id PRIMARY KEY, request_hash, thread_id UNIQUE, state, ...)
worker_inputs(message_id PRIMARY KEY, thread_id, request_hash, record_cbor, state, ...)
worker_decisions(approval_id PRIMARY KEY, thread_id, request_hash, state, ...)
worker_cancels(cancel_id PRIMARY KEY, thread_id, request_hash, state, ...)
```

These are durable outbox/idempotency rows, not a conversation model. Their
dispatcher invokes the existing executor and recovers accepted-but-not-applied
rows after worker restart. Where exact-once application needs a source ID in the
ledger, the smallest compatible metadata field is added to the existing append
path; no parallel log is created.

### Node identity and placement

The local coordinator owns `node_id`, `node_attempt_id`, `remote_id`, and
`operation_id`. The worker health record echoes reserved node/attempt identity.
The worker conversation identity is its returned existing thread ID.

Placement policies:

- `fresh_node`: provision then create;
- `prefer_existing`: choose a compatible known node with capacity;
- `require_node`: target one node or fail.

MVP defaults to `fresh_node`, while acceptance tests prove two thread IDs can
run on one `require_node`. Switching the default later requires no worker
schema migration.

### Concurrency and limits

Reuse the existing per-thread workers. Add only:

- a bounded control-command channel;
- per-thread bounded prompt ingress;
- a node-wide active-turn permit limit around `module.run`;
- optional per-provider completion limits at the existing completion Store;
- Wasmtime memory/fuel/epoch limits configured in `ox-runtime`;
- cancellation handles for active Wasm calls and sandboxed tool subprocesses;
- bounded cursor reads and transport frames.

Turn permits gate execution, not status, approval, cancellation, or ledger
reads. A worker blocked on approval has already yielded its active-turn permit
or uses a separately accounted waiting state; it cannot consume all control
capacity. FIFO admission is sufficient for MVP—do not build weighted fair
queueing without measured need.

### Transport

Wire v1 is length-prefixed canonical CBOR carrying StructFS read/write
requests, paths, records, deadlines, responses, and typed errors. Requests may
be in flight concurrently and responses may arrive out of order.

MVP uses one multiplexed RuSSH exec channel because cursor batches and ordinary
records are bounded. A second bulk channel is added only when artifact byte
transfer lands and measurements show it is needed. The stdio bridge is
stateless; EOF detaches and never shuts down `ExecutionCore`.

## State and writer ownership

### Local orchestration state

```text
accepted -> provisioning -> booting -> connecting
         -> creating -> running <-> waiting_for_input
                                <-> blocked_on_approval
         -> cancelling -> completed | failed | cancelled | lost
```

This state belongs to the local `RemoteManagerStore` replica. The authoritative
remote conversation state remains the worker's existing inbox/thread/log.

### Authoritative writers

| Record | Writer | Key/order |
|---|---|---|
| local remote intent/node state | local `InboxStore` | operation/node/attempt IDs |
| exe.dev VM | provider via `ExeControlStore` | deterministic VM name + exact reconcile |
| worker thread row | worker `InboxStore` | existing `t_...` ID |
| worker ingress intent | worker `InboxStore` | create/message/approval/cancel semantic ID |
| conversation log | existing per-thread `LedgerWriter` | ledger seq/hash chain |
| config snapshot | existing `save_config_snapshot` | existing turn boundary |
| approval runtime state | existing `ApprovalStore` | thread approval path |

There is no `node.db`, `events.jsonl`, placement catalog on the worker, or
conversation child manifest.

| reusable executor | new `crates/ox-executor/`, moved from `ox-cli` without behavior change |

| CLI | headless command dispatch in `crates/ox-cli/` |
| image | `images/ox-worker/`, build script |

Dependency rules:

- `ox-executor` depends on existing runtime/kernel/tools/inbox/broker crates,
  never Ratatui or crossterm;
- both `ox-cli` and `ox-worker` depend on `ox-executor`;
- `ox-structfs-transport` knows StructFS and carriers, not conversations;
- `ox-remote` knows remote records and abstract Stores, not UI;
- only `ox-inbox` changes ox-owned SQLite schemas;
- RuSSH command knowledge stays in carrier/exe adapter modules.

## Acceptance scenarios

- [ ] The same scripted prompt produces semantically identical ledgers through
  local CLI and remote worker.
- [ ] Two worker conversations use distinct existing thread directories,
  ledgers, approvals, and workspaces in one `ExecutionCore`.
- [ ] An unresolved approval in A does not delay B's prompt or C's cancel.
- [ ] A Wasm trap affects its turn and log, not another conversation.
- [ ] A sandboxed tool timeout kills that invocation and leaves the worker
  process and other conversations healthy.
- [ ] Worker restart uses existing restore/classify/resume code and replays
  accepted ingress without duplication.
- [ ] SSH disconnect never stops a turn; reconnect resumes from ledger seq/hash.
- [ ] Two local CLIs racing one operation converge through durable IDs.
- [ ] Changed host keys and missing sandbox enforcement fail closed.
- [ ] Node deletion refuses active threads.
- [ ] No remote path reaches `secret/`, arbitrary `threads/` internals, tools,
  filesystem, or broker root.

---

## Explicit non-goals

- A second executor, scheduler, thread registry, durability layer, or event log.
- A per-conversation OS process or container.
- Implementing the future full Isotope runtime in the remote project.
- Flutter, Android, Kotlin, or mobile background integration.
- Arbitrary SSH exec, shell, forwarding, SCP, or SFTP.
- Repository writeback or pull-request automation.
- Cross-node live migration of an executing turn.
- A local notification daemon.
- Artifact byte transfer before a real use case requires the bulk lane.

## Shortest path and estimate

```text
extract existing ExecutionCore
  -> harden existing sandbox/cancellation
  -> idempotent ingress
  -> wire + local carrier
  -> thin WorkerPublicStore
  -> RuSSH/exe adapters
  -> local reconciliation
  -> CLI/image
```

The pre-provisioned proof is Tasks 0-6. The useful exe.dev MVP is Tasks 0-10.
Because this version reuses the executor and its durability/recovery stack, the
expected MVP effort is approximately **6-9 engineer-weeks**, followed by
2-3 weeks of soak, security, and rollout hardening. Measurements should revise
that estimate after Task 1 exposes the true extraction seam.
